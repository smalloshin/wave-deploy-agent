## Decision

### R57.1 — race window 15 → 25 min

`reconciler-recovery.ts:64`：
```typescript
export const RECONCILER_RACE_WINDOW_MS = 25 * 60 * 1000;  // 原 15 min
```

R57 加 Step 3.5 migration 後 deploy 整體時間從 9 min 漲到 12-15 min（migration job cold start 30-90s + 實際跑 schema migration 1-3 min）。15 min race window 踩在臨界值，reconciler 會誤判 deploying-but-actually-running 的 deploy 為 stuck 提早 mark failed。25 min 給 buffer。

trade-off 還是一樣：真卡死的 deploy 多等 10 分鐘介入完全沒 user impact（沒 Cloud Run service materialize = 沒流量影響），但 false-positive 把好的 deploy 標 failed 直接弄死該次部署。

Tests：default deployment 從 20 min 改 30 min（要 well past window），加一個 `24 min ago → still skip` 的 regression guard。

### R57.2 — `wave_deploy_migrations` cleanup cron

新 `services/migration-cleanup.ts`（120 LOC pure 函式 + 11 zero-dep tests）：

```typescript
export async function cleanupMigrationRows(
  query: DbQueryFn,
  options: { retentionDays?: number } = {},
): Promise<{ expiredSweeped: number; rowsDeleted: number; summary: string }>;
```

兩件事：

1. **TTL sweep**：UPDATE rows 的 `status='running'` AND `expires_at < NOW()` → 設為 `status='expired'`。
   - 目的：worker crash 時 row 會卡在 'running'，unique partial index `(project_id) WHERE status='running'` 會 block 該 project 後續所有 deploy 直到手動 fix
   - 加 `COALESCE(error_message, ...)` 不覆蓋既有 message
   - `finished_at = NOW()` 標記何時 expire

2. **Retention delete**：DELETE rows 的 `created_at < NOW() - 30 days` AND `status != 'running'`
   - 預設 30 days，可調 `retentionDays`
   - 設為 0 → sweep-only 模式（不 delete）
   - **不刪 running rows**（保護機制，TTL 會先 sweep 過去）

Wired in：reconciler.ts 加 `tickCount % CLEANUP_EVERY_N_TICKS === 0`（每 30 tick = 每小時跑一次）。Reconciler tick 是 2 min 一次，60 min 一次 cleanup，TTL = 15 min，最差 case row 卡 ~75 min（一個 tick + 一個 cleanup window）才被 sweep — 接受。

Pure-ish 設計：函式吃 `query` callable，方便測試 + 換 DB client。Never throws — DB error 進 summary 字串，reconciler tick 不會 crash。

### R57.3 — 5 個新 migration framework

`migration-detector.ts` 從 4 verdict 變 9：

| Tool | Detection | Command |
|------|-----------|---------|
| `django` (新) | `manage.py` + `Django` in requirements / pyproject | `python manage.py migrate --noinput` |
| `flask_migrate` (新) | `Flask-Migrate` dep OR (`Flask` dep + `migrations/env.py` 存在) | `flask db upgrade` |
| `drizzle` (新) | `drizzle.config.{ts,js,mjs,json}` + `drizzle-kit` in deps | `npx drizzle-kit migrate` |
| `knex` (新) | `knexfile.{js,ts,cjs,mjs}` + `knex` in deps | `npx knex migrate:latest` |
| `typeorm_manual` (新) | `typeorm` dep + `data-source.{ts,js}` 存在 | `null` (warn + skip) |

新 helper：
- `hasPythonDep(projectDir, namePattern)`：parse `requirements.txt` + `pyproject.toml`，正則 match dep 名（用 `(?![A-Za-z0-9_-])` lookahead 防止 `django-rest-framework` 誤命中 `^django`）
- `hasNodeDep(projectDir, depName)`：parse `package.json` deps + devDeps（exact-name match）

#### TypeORM 為什麼是 manual

TypeORM 的 migration command 需要 `-d <data-source>` 但 data-source 路徑因 project 而異（`data-source.ts` / `src/data-source.ts` / `src/db/data-source.ts` 都有見過），auto run 容易選錯造成 schema drift。寧可偵測到後 emit warning 跳過，user 自己決定。Future R57.3.x 加 `project.config.migrationCommand` 覆寫支援。

#### Priority 順序

Detection 從上往下：Prisma → Alembic → Django → Flask-Migrate → Drizzle → Knex → TypeORM。多個 markers 同時存在時（罕見但可能：monorepo 有 Node + Python），第一個 hit 贏。寫進測試 `Prisma + Django markers → Prisma wins`。

#### Cloud Run Job orchestration 怎麼跑這 5 個

`cloudrun-jobs-migration-runner.ts` 改 early-skip 條件：原本 `if (verdict.tool === 'none' || verdict.tool === 'prisma_db_push_only')` 改成 `if (verdict.command === null)`。這樣 `none` / `prisma_db_push_only` / `typeorm_manual` 都自動 skip，剩 6 個有 command 的都進 Cloud Run Job 跑。

## Consequences

**好處**：
- R57.1：12-15 min 的大型 deploy 不會被 reconciler 誤殺
- R57.2：worker crash 時 stale row 1.25 hr 內 sweep + 30 天前 audit row 自動清，table 不會無限長
- R57.3：原本只支援 Prisma + Alembic 兩種，現在支援 8 個 first-class（含 TypeORM 偵測但 skip）。Vibe-coded 用 Django / Drizzle / Knex 的專案直接 supported

**代價**：
- R57.1：真卡死的 deploy 多等 10 min。已知接受
- R57.2：每小時多兩個 SQL（一個 UPDATE 一個 DELETE），DB 負擔忽略
- R57.3：detector 從 4 到 9 verdict，code 多 ~120 LOC + tests 多 ~150 LOC。判斷邏輯加深但每個 branch 仍然 deterministic
- 沒處理：TypeORM auto-run（v2）、Sequelize（沒 vibe-coder 用過，跳）、Mikro-ORM（同）
